# UPI 账单反查与指定提交对比

本文记录核查时的本地工作区，包含未纳入本次 GitHub 提交的账单相关修改；文中的当前行为和行号属于该核查快照，不代表发布版本已包含这些修改。

核查日期：2026-10-15。基线为确切 Git 提交 `8d25555472177109392758b9516bf0e7c8fc1bf5`，通过本地 Git 对象读取。比较对象为本次读取时的工作区，不以附件 UPI6 代替基线。

结论：账单准备与字段来源存在实质变化；这与此前确认的遥测、指纹及支付提交函数源码一致并不矛盾。相同提交函数可以收到不同账单数据。现有证据不足以认定反查是 `upi_risk_blocked` 的原因。

## 主要差异

| 项目 | 指定提交 | 当前工作区 |
|---|---|---|
| 未提供地址时的来源 | 本地地址池 | 接受的反查结果优先，否则回退本地池 |
| 调用方完整地址 | 优先保留，通过本地输入校验 | 优先保留，通过本地输入校验及五地区限制 |
| 代理位置查询 | 可选探测城市以匹配池，默认关闭 | 增加代理 IP 的国家和坐标探测，然后调用 Nominatim reverse；反查默认开启 |
| 静态主池 | 78 条、49 城市、24 地区 | 32 条、15 城市、五地区；这些数字不包含合并的其他静态来源及可选外部文件 |
| 地区范围 | 印度多个地区 | Delhi、Karnataka、Maharashtra、Tamil Nadu、West Bengal |
| 无调用方姓名时 | 既有姓名池 | 接受的反查结果有地点名时使用地点名，否则既有姓名池 |
| 内部重新建单 | 未指定地址时重新抽池 | 接受的反查地址在循环外确定，内部重建复用；回退池仍重新抽取 |
| 反查缓存 | 无此路径 | 坐标精确到小数点后五位作为键，TTL 30 天，最多 5000 条 |

当前链路的开关是 `UPI_BILLING_REVERSE`，默认开启；任务参数 `upiBillingReverse` 可覆盖它。先前提到的 `PAY153_INDIA_REVERSE_ENABLED` 不是当前这条 UPI 调用路径读取的开关。

## 已确认的字段语义问题

`billing_address_resolver.py:241` 从 `amenity/building/shop/tourism/payload.name` 提取地图地点名称，并在第 271 行以 `name` 返回。`upi_link_service.py:716` 传递这个字段，随后第 3187 行在调用方未提供姓名、且反查地址被接受时，将其作为账单姓名。

该值随后实际进入支付请求的姓名字段：`upi_link_service.py:3938`、`:4737` 的 `billing_details[name]`，以及 `:5516` 的 `billing_name`。地点名可能是商店或建筑名称，不能据此确定付款人姓名。指定提交的旧规范化函数没有这条来源。

这是确定的字段语义差异。正确的数据边界应把地图地点名与付款人姓名分开；真实支付的身份与账单地址应以付款人提供或授权的数据为依据。不能从此次代码比较推断替换某种姓名或地址就能通过审核。

## 反查、过滤与校验

- `upi_link_service.py:644` 经任务支付代理请求 IP 地理位置，只有国家为 `IN` 才进入地图反查。代理 IP 坐标并不等于付款人的街道地址。
- `billing_address_resolver.py:186` 调用 Nominatim `/reverse`，使用英文结果、`zoom=18`、`addressdetails=1`，另带 `layer=address`。地图请求没有显式传入支付任务代理；不能据此排除运行环境的系统代理设置。
- `upi_link_service.py:688` 和 `:3213` 都要求街道、城市、允许的州及有效格式的六位邮编。缓存结果也经过这些过滤，区外缓存不能直接进入付款地址。
- 地图字段缺失时整条回退，不用 IP 地理查询返回的城市、州或邮编拼补地图地址。
- 反查仅检查上述字段及格式，不检查城市—州—邮编前三位关系；调用方显式地址还经过本地已知组合检查。两种检查均不是完整的邮政地址认证。
- 反查在认证和内部重建循环前执行；接受的结果跨该次调用的内部重建复用。外层 Worker 重试会创建新引擎进程，不应把内部复用理解成所有任务永久复用。

首次 Checkout 创建请求的账单信息只有国家 `IN` 和币种 `INR`，见 `upi_link_service.py:5316`。完整姓名和地址在后续税费、账单快照、支付确认中使用。因此不能把首次建单被拒直接解释为该请求中的街道、邮编发生变化。

## 缓存与并发限制

`billing_address_resolver.py:186` 使用 `threading.Lock` 和 1.05 秒间隔；这是进程内限速。`backend/app/engine_adapter.py:607` 为执行项启动独立子进程，所以多个并发任务没有共享的全应用限速。

`billing_address_resolver.py:171` 写入同一缓存路径及固定 `.tmp` 临时文件，缓存锁同样为进程内锁；跨进程读改写可能相互覆盖或发生写入失败，异常会被吞掉。这是代码层面的并发风险，本次没有证据确认实际触发了地图限流或缓存冲突，更不能将其等同于支付接口风控。

本次读取默认反查缓存共 22 条，其中 8 条属于五地区、14 条在五地区之外；17 条带非空地点名称。解析器先缓存地图结果，UPI 层再过滤，因此缓存包含区外记录并不代表这些记录被提交。缓存内容也不能证明某条任务最终用了其中哪条记录。
