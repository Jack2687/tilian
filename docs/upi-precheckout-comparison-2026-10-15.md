# UPI 建单前代码与指定提交的比较

本文记录核查时的本地工作区，包含未纳入本次 GitHub 提交的账单相关修改；文中的当前行为和行号属于该核查快照，不代表发布版本已包含这些修改。

比较日期：2026-10-15。

基线是本地 Git 对象中的确切提交 `8d25555472177109392758b9516bf0e7c8fc1bf5`，通过 `git show <commit>:<path>` 读取。比较对象是当前工作区，包括尚未提交的修改。这次没有把附件的 `tilian_upi6` 修改版当成基线。

范围从 `extract_upi_link()` 进入，覆盖认证、优惠预检、账单准备、页面预热、请求头、客户端选择，直到第一次 `POST /backend-api/payments/checkout`。仅做文本与 Python AST 静态检查，没有执行支付请求。

## 结论

**真正发送建单请求的 `_run_upi_attempt()` 与指定提交完全一致；当前建单前的实质变化集中在账单来源及其前置查询。** 认证、优惠预检、页面预热、客户端/TLS 选择、请求头和建单 JSON 的代码没有变化。

初次建单 JSON 只包含账单国家 `IN`、币种 `INR` 等结账信息，不包含街道、城市、州或邮编。因此地址来源变化不会直接改变这一次 POST 的地址字段；它增加了建单前的查询步骤，并改变后续税区、账单快照和确认阶段复用的地址。

## 已变化的账单准备

| 项目 | 指定提交 | 当前工作区 | 工程影响 |
|---|---|---|---|
| 允许地区 | 本地池覆盖多个州/地区 | 限定 Delhi、Karnataka、Maharashtra、Tamil Nadu、West Bengal | 缩小可用地址范围 |
| 硬编码候选 | 78 条 | 32 条 | 这是硬编码候选数，最终池还合并 resolver 和有效外部记录 |
| 外部地址文件 | 无此入口 | 支持 `UPI_BILLING_POOL_FILE` | 地址数据可以通过文件进入既有合并、格式校验、去重流程 |
| 未填写地址时 | 直接选择本地候选；可选同城查询 | 优先尝试出口坐标反查，失败或不满足五地区规则时回退本地池 | 增加前置外部请求和等待时间，结果仍需格式与地区过滤 |
| 出口信息 | 通过共享 helper 获取城市 | 获取并缓存国家、城市、经纬度 | 为反查提供坐标；没有更改支付客户端的 TLS 配置 |
| 地址优先级 | 调用方地址 → 本地池 | 调用方地址 → 有效反查地址 → 本地池 | 显式填写地址仍优先 |
| 步骤日志 | 城市/州/邮编 | 城市/州/邮编及来源 | 能区分调用方、反查和本地池 |

当前的主要位置：

- 地区名单：`upi_link_service.py:405`。
- 外部文件读取：`upi_link_service.py:505`、`:509`、`:541`、`:559`。
- 合并与地区过滤：`upi_link_service.py:595`。
- 出口信息查询：`upi_link_service.py:644`。
- 反查入口及五地区过滤：`upi_link_service.py:688`、`:713`。
- 地址优先级：`upi_link_service.py:3163`。
- 反查字段二次过滤：`upi_link_service.py:3213`。
- 认证前的反查调用：`upi_link_service.py:3303`。
- 每次尝试构造统一账单：`upi_link_service.py:3412`。

反查默认由 `UPI_BILLING_REVERSE` 控制。显式地址存在时不需要这一步；反查无结果、字段不完整或州不在名单内时，不将该反查结果作为账单，而是继续使用本地池。单次入口先冻结通过检查的反查结果，后续尝试复用该结果。

## 比较边界

这里确认的是代码是否相同及其输入/输出差异。环境变量、调用参数、依赖版本、代理连通性和上游服务状态仍可能使相同代码产生不同结果。静态比较不能证明两边成功率相同，也没有进行真实建单来测量差异。

本次增加的交付结果校验属于建单之后的后台边界，不会改写这里比较的初次 Checkout 请求。
